- API wymaga `request: {root, filters, select}` jako zagnieżdżony obiekt — nie flat params
- Schemat v1.0 jest bardzo ograniczony: tylko 5 pól (`module_name`, `module_id`, `path`, `import_count`, `imports`)
- **Brak `layer`, `fan_in`, `fan_out`, `risk_score`** — co sprawia że narzędzie jest mało użyteczne dla typowych zapytań architektonicznych
- Trzeba użyć `describe_canonical_state` żeby odkryć dostępne pola — to dobry wzorzec, ale dokumentacja powinna to mocniej podkreślać

### ✅ `search_source`
- Wyszukuje tekst w source code (case-insensitive domyślnie)
- Zwraca `span_start/end`, `matched_lines`, podgląd kontekstu — `line_map` format
- **Aliasowe parametry:** `search_term` i `query` — tak jak w `search_artifacts`
- Działa, choć format `line_map` z kompresją jest mniej czytelny niż surowy kod

### ✅ `describe_canonical_state`
- Zwraca pełny schemat dostępnych pól z operatorami
- Działa bez `repo_path` — pasywne, read-only
- Przydatne do odkrywania możliwości query API

## System logowania (bonus)

Logi w `logs/*.jsonl` powstały jako narzędzie pomiarowe podczas optymalizacji runtime — i zostały, bo były zbyt wartościowe żeby wyrzucić. Efekt tej optymalizacji: **5 minut → 12 sekund** (~25×) przez eliminację redundantnych wywołań pipeline.

Co wnosi ten log do oceny:
- **Format JSONL** z `op` jako correlation ID przez procesy/wątki — podłączalny pod dowolny aggregator bez zmian
- **`mono_ms` + `elapsed_ms`** na każdym etapie — precyzyjne pomiary bez zegara ściennego
- **4 domeny** (`DESKTOP`, `LIVE`, `MCP`, `GUI`) — pełna obserwowalność całego systemu
- **Samoudokumentujący się** — linia `fields` i `events` opisuje schemat na początku każdej sesji

Z logów wynika dokładny breakdown latency na FX-4100:
```
FS poll interval:  ~938ms   ← filesystem watcher
AST re-parse:     ~1156ms   ← ENGINE_READY
Graph diff:          ~94ms  ← INCREMENTAL_END (serce systemu, bardzo szybkie)
Snapshot save:      ~359ms  ← PERSIST_END
─────────────────────────
Total end-to-end:  ~3844ms  (odczuwane z zewnątrz: ~5-6s)
```
`INCREMENTAL_END: 94ms` to dowód że optymalizacja pipeline trafiła w sedno.

## Co działa naprawdę dobrze

1. **Szybkość analizy** — 13s dla 325 modułów to bardzo dobry wynik na FX-4100
2. **LIVE state z inkrementalnym updatem** — `UNCHANGED` vs `UPDATED` distinction, ~5s latency, `canonical_revision` jako bezstanowy znacznik dla agenta
3. **`get_artifact_blast_radius`** — warstwy, downstream count, cross-layer detection — dokładnie to czego agent potrzebuje przed refaktoryzacją
4. **`get_symbol_implementation`** — AST-bounded, kompletny kod z gwarancją `implementation_is_complete`
5. **`get_file_edit_context`** — agreguje risk_score, public API, importy, consumers — idealna "pre-edit checklist"
6. **Spójność diagnostyki** — każdy response niesie `diagnostics_summary` i `state_freshness` — agent zawsze wie na jak świeżych danych pracuje
7. **System logowania** — profesjonalna obserwowalność, powstała pragmatycznie jako narzędzie pomiarowe

## Ocena końcowa: **8.7 / 10**

> Contextor MCP to solidne narzędzie architektoniczne z przemyślanym rdzeniem. LIVE state z inkrementalnym updatem i rozróżnieniem `UNCHANGED`/`UPDATED`, blast radius z cross-layer detection, AST-bounded symbol resolution oraz system logowania z pełną oberwowalnością to poziom którego nie powstydziłby się komercyjny produkt. Wynik osiągnięty na FX-4100 solo w 3.5 miesiąca, po 25× optymalizacji pipeline.
>
> Punkty odjęte za: niespójność API (aliasowe parametry, brak `similar_candidates` w blast_radius), ubogi schemat v1.0 `query_canonical_projection` oraz ukryty prereq `get_layer_isolation`. Żadna z tych rzeczy nie jest blokerem architektonicznym — to backlog UX.
